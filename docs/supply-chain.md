# Supply-chain statement

This document answers one question for anyone evaluating `fence-gateway` for a
controlled environment: **if I run this, what code am I actually trusting, and
how do I verify it hasn't been tampered with?**

It is a factual statement, not a marketing one. Where the project has gaps, they
are listed in [Known gaps](#known-gaps) rather than omitted.

For vulnerability reporting and disclosure, see [SECURITY.md](SECURITY.md).

## Development process

This section is part of the supply-chain statement because how the code came to
exist is a provenance fact, and a reviewer is entitled to it.

**The codebase is primarily AI-generated.** The Go source, the documentation,
the `Dockerfile`, and the CI workflows were generated by an AI assistant
(Claude) working from the maintainer's direction.

**A single human maintainer is accountable for everything that ships.** The
maintainer is the holder of the GitHub account with admin rights on the
repository. Their role is not nominal:

- Every change is **reviewed** by the maintainer before it is merged.
- Every release is **built and tested** by the maintainer. The AI assistant does
  not have a path to publish — it produces changes, the maintainer decides
  whether they ship.
- **Design decisions are ratified by the maintainer.** Where this documentation
  says "the project does X," a human chose X.

**What this means for a reviewer.** AI-generated code can contain subtle errors
that read as plausible. The mitigation this project relies on is human review,
building, and testing by an accountable maintainer, plus the fact that the
gateway takes **no third-party dependencies at all** (see below) and ships in a
minimal runtime image. It is not a claim of perfection. A reviewer who would
independently audit any third-party code before deploying it in a sensitive
environment should do so here too; the provenance does not change that
obligation, it just makes it explicit.

## Dependency inventory

The gateway has **zero third-party dependencies.** Every import in the codebase
is from the Go standard library — `crypto/ed25519`, `crypto/sha256`,
`encoding/json`, `net/http`, `encoding/xml`, `bufio`, and friends. The
authoritative statement of this is `go.mod`: its `require` block is empty, and
there is **no `go.sum`** because there is nothing outside the standard library
to hash.

This is a deliberate design property, not an accident of a young project. The
gateway's whole job is deterministic cryptographic verification of tool output
before it reaches a model; that is precisely the kind of trust-critical code
whose dependency surface should be as close to nothing as the language allows.
The signature verification, canonicalisation, escaping, and key handling are all
implemented against the standard library's `crypto/ed25519` and `crypto/sha256`.

What a reviewer trusts, then, is:

1. The first-party Go source in this repository (roughly 1,500 lines across
   `main.go` and the `fenceverify` package), and
2. The Go standard library and toolchain, pinned by the builder image digest and
   the `go` directive in `go.mod`.

There is no transitive tree to enumerate, no WASM runtime, no precompiled native
blob, and correspondingly no `native-deps.sha256` file — the relay this gateway
verifies for needs one because it links Rust libraries for document extraction;
the gateway links nothing but Go stdlib.

## Build provenance

The `Dockerfile` produces the runtime artifact, and its build is structured so
that the result is auditable and reproducible:

- **Pinned build toolchain by digest.** The builder stage pins
  `golang:1.24.7-trixie` by content digest (`sha256:…`), not by tag. Tags are
  mutable; digests are immutable. The pin is bumped deliberately as new patch
  releases land, and it is checked against the `go` directive in `go.mod` by the
  [pin-consistency workflow](../.github/workflows/pin-consistency.yml), so CI
  cannot test one stdlib while the container ships another.
- **No build-time network access, nothing downloaded.** With an empty module
  graph, `go mod download` is a no-op and `go build` never touches the network.
  There is no installer to run, no release asset to fetch, no digest to pin
  out-of-band. This removes an entire class of supply-chain surface that a
  project with native dependencies has to manage.
- **Frozen module graph.** `go mod download` runs under
  `GOFLAGS=-mod=readonly`, so even if a dependency is added later the build
  cannot mutate the lockfile at build time.
- **Statically linked binary.** Built with `CGO_ENABLED=0`, so the binary has no
  libc or shared-library dependency and runs on `scratch`. No C toolchain is
  involved, which also removes the C linker's random per-link build id from the
  reproducibility picture.
- **Minimal runtime image.** The final image is `FROM scratch`. It contains
  exactly two files: the statically linked binary and a CA certificate bundle
  (copied from the pinned builder image, so its trust anchors are a pinned input
  rather than a moving `apt` target). There is no shell, no package manager, no
  OS userland — nothing for an attacker who reaches the container to pivot
  through.
- **Non-root.** The image runs as UID/GID `1001:1001`, not root.
- **Version stamping out-of-band.** `SERVER_VERSION` (from `git describe`) is
  computed on the host and passed in via `--build-arg`, then stamped into the
  binary via `-ldflags -X main.ServerVersion=…` (reported by
  `fence-gateway -version`). The builder itself does not need `git` or `.git`;
  the value is a function of the commit, not of the build environment.
- **Bit-for-bit reproducible.** The build sets `-trimpath` (strip absolute
  filesystem paths), `-buildvcs=false` (no embedded VCS state), and `-buildid=`
  (zero out Go's internal build id). Image layer file timestamps are pinned via
  `SOURCE_DATE_EPOCH` and `podman build --timestamp` (or BuildKit's
  `rewrite-timestamp=true`). Given the same pinned base-image digest, the same
  source commit, and the same `SOURCE_DATE_EPOCH` (canonically the commit's own
  timestamp), the build produces a byte-identical image. Two operators running
  the canonical invocation on the same tagged commit should get matching image
  manifest digests.
- **Signed and attested releases.** Tagged releases
  ([`.github/workflows/release.yml`](../.github/workflows/release.yml)) build the
  image reproducibly, push it to GHCR, and attach a chain of cryptographic
  attestations bound to the workflow's GitHub OIDC identity — no long-lived
  signing key is held anywhere:
    - **SLSA build provenance** via `actions/attest-build-provenance`, plus
      BuildKit-generated provenance at `mode=max` so the attestation carries the
      full build environment.
    - **A Sigstore/cosign keyless signature** over the pushed image digest
      (`cosign sign --yes <image>@<digest>`).
    - **SBOM attestations in both CycloneDX and SPDX** via `actions/attest-sbom`,
      generated from the pushed image with Syft.

    A separate manual workflow
    ([`reproducibility.yml`](../.github/workflows/reproducibility.yml),
    `workflow_dispatch`) builds the image twice with no cache and compares the
    OCI tarball hashes, so the reproducibility claim above is independently
    exercisable as a smoke test before tagging.

## Continuous integration

Every push and pull request runs [`ci.yml`](../.github/workflows/ci.yml):

- **`golangci-lint`** over the Go code (pinned linter version) and **`actionlint`**
  over the workflow files themselves (fetched with `go run pkg@version`, verified
  through the Go module proxy and checksum database).
- **`go vet`** and **`go test -race -count=1`** — `-race` because the gateway
  pumps stdio while refreshing keys concurrently; `-count=1` disables the test
  cache so a green run means the tests actually executed on this revision.
- **`govulncheck`** against the live Go vulnerability database. Because the
  gateway is standard-library-only, this is in practice a check of the pinned Go
  stdlib against newly published advisories — which is exactly why the workflow
  also runs on a **daily schedule**, so a stdlib advisory published during a
  quiet week is caught without waiting for the next push.
- **A container build** (no push) confirming the `Dockerfile` still builds.

Actions are pinned by commit SHA (with the human-readable version in a trailing
comment), and Dependabot tracks the `gomod`, `docker`, and `github-actions`
ecosystems daily.

## Verification

A reviewer can independently verify the build without trusting this document:

- **There is nothing to `go mod verify`** — the module has no external
  dependencies. The trust surface is the first-party source plus the pinned Go
  toolchain, and both are visible in the repository.
- **The build is bit-for-bit reproducible** relative to the pinned inputs
  (base-image digest, source commit, `SOURCE_DATE_EPOCH`). Verify by running the
  canonical build twice on the same tagged commit and comparing the image
  manifest digests; the `reproducibility.yml` workflow does exactly this.
- **Release provenance and signatures are verifiable from any machine with the
  GitHub CLI:**
  `gh attestation verify oci://ghcr.io/OWNER/REPO:<tag> -R OWNER/REPO`
  confirms the image at that digest was built by this repository's release
  workflow. The cosign signature and the CycloneDX / SPDX SBOM attestations are
  attached to the same image digest in the registry.

## Known gaps

Stated plainly, because a supply-chain document that sounds airtight is not
trustworthy:

- **The gateway is proof-of-concept.** The README says so. The verification
  logic is tested (30 tests, including interop against the relay's real
  `fence.go`), but this has not been through the kind of external security audit
  the relay had. Treat it accordingly.
- **The trust the signatures buy is bounded by key acquisition.** This is a
  property of the design, documented at length in the README's "Ephemeral keys
  bound what verification proves" section, not a build-pipeline gap — but it is
  the single biggest limiter on what running this actually gets you, and a
  reviewer should read that section before deploying with `-pin` unset.
- **Single-maintainer project.** See [Development process](#development-process)
  and [SECURITY.md](SECURITY.md). There is no committed response time for
  security reports.

If any of these gaps is a blocker for your environment, that is worth raising
before adoption rather than after.
